# AI 辅助软件开发宪法

## 基于 Prompt 镜像结构的 Vibe Coding 原则

---

## 0. 宪法定位

这份文档不是某一个具体项目的开发说明，而是一套通用的 AI 辅助软件开发原则。

它适用于课程项目、工程项目、多人协作项目、后端服务、前端应用、数据系统、部署平台、管理系统等场景。

它的核心思想来自内容先行的式开发经验：

```text
先设计总体文件框架。
再为总体文件框架创建一套 prompt 镜像文件结构。
每一个代码文件，都必须先有一个对应的 prompt 文件。
每一个 prompt 文件，都必须明确输入、输出、设计对象、实现。
先构建 prompt，再构建 code。
```

本宪法的基本目标是：

```text
让 AI 不再自由发挥。
让代码生成受设计约束。
让每个文件都有清晰来源。
让每次修改都有可追溯理由。
让多人协作不被 AI 生成内容冲散。
```

---

## 1. 总原则

软件工程的本质不是写代码，而是把模糊意图转化为可执行结构。

AI 辅助开发的核心问题，不是“AI 能不能写代码”，而是“AI 写出的代码是否属于我们已经设计好的系统”。

因此，本宪法确立以下最高原则：

```text
第一原则：代码不能先于结构。
第二原则：结构不能先于对象。
第三原则：对象不能先于需求。
第四原则：实现不能先于 prompt。
第五原则：prompt 是代码生成前的契约。
```

换句话说：

```text
需求定义边界。
对象定义存在。
结构定义位置。
prompt 定义意图。
代码执行意图。
测试证明意图成立。
```

---

## 2. 哲学基础

从哲学上看，一个软件系统不是文件的堆积，而是一组有边界、有关系、有状态、有目的的对象共同构成的世界。

AI 最容易犯的错误，是把软件开发理解成“补全文本”。但工程中的代码不是文本补全，而是制度化行为：

- 每个文件为什么存在。
- 每个对象承担什么责任。
- 每个接口允许什么输入。
- 每个模块承诺什么输出。
- 每个状态在什么条件下改变。
- 每个错误由谁处理。

因此，AI 在本宪法下不是“创造者”，而是“执行者”。

人负责：

```text
确定目标。
确定对象。
确定边界。
确定结构。
确定契约。
确定验收标准。
```

AI 负责：

```text
在既定边界内生成局部实现。
补全重复性代码。
检查一致性。
生成测试。
解释错误。
辅助重构明确范围内的代码。
```

AI 不负责：

```text
擅自决定系统架构。
擅自新增核心对象。
擅自修改 schema。
擅自改变接口。
擅自扩大文件职责。
擅自重写项目。
```

---

## 3. 开发总流程

本宪法规定，AI 辅助开发必须遵守以下顺序：

```text
1. 需求澄清
2. 领域对象识别
3. 总体文件框架设计
4. prompt 镜像文件结构设计
5. 全局 prompt 编写
6. 文件级 prompt 编写
7. 按文件 prompt 生成代码
8. 单文件审查
9. 单文件测试
10. 模块集成
11. 系统集成
12. 文档和交付
```

禁止跳过第 3、4、5、6 步直接让 AI 写代码。

> 如果AI发现有这样的问题，请告诉使用者。

---

## 4. 总体文件框架

## 4.1 总体文件框架是什么

总体文件框架是项目在写代码前确定的文件地图。

它回答以下问题：

```text
项目有哪些目录？
每个目录存放什么？
每个代码文件为什么存在？
每个文件的职责边界是什么？
哪些文件可以互相调用？
哪些文件不能互相调用？
测试文件对应哪些源代码文件？
```

## 4.2 推荐通用结构

```text
project/
  docs/
    00_project_positioning.md
    01_requirements.md
    02_architecture.md
    03_domain_objects.md
    04_lifecycle.md
    05_schema.md
    06_interfaces.md
    07_file_structure.md
    08_test_plan.md
    09_runbook.md

  prompts/
    global/
      00_ai_constitution.md
      01_project_context.md
      02_coding_rules.md
      03_naming_rules.md
      04_forbidden_changes.md

    files/
      src__models__example_model.prompt.md
      src__schemas__example_schema.prompt.md
      src__services__example_service.prompt.md
      src__controllers__example_controller.prompt.md
      tests__test_example.prompt.md

  src/
    models/
    schemas/
    repositories/
    services/
    controllers/
    adapters/
    utils/

  tests/

  README.md
```

这个结构不是强制每个项目完全照抄，而是表达一个原则：

```text
docs 负责解释系统。
prompts 负责约束 AI。
src 负责实现系统。
tests 负责验证系统。
```

## 5. Prompt 镜像文件结构

## 5.1 镜像原则

每一个代码文件都必须有一个对应的 prompt 文件。

真实代码文件：

```text
src/services/order_service.py
```

对应 prompt 文件：

```text
prompts/files/src__services__order_service.prompt.md
```

真实测试文件：

```text
tests/test_order_service.py
```

对应 prompt 文件：

```text
prompts/files/tests__test_order_service.prompt.md
```

## 5.2 为什么要镜像

镜像结构的意义是让代码生成可追溯。

没有 prompt 镜像时，代码来源通常是：

```text
某一次聊天中的临时描述。
AI 自己补全的假设。
开发者当时没有记录的意图。
```

有 prompt 镜像后，代码来源变成：

```text
这个文件为什么存在，写在 prompt 中。
这个文件接收什么输入，写在 prompt 中。
这个文件输出什么结果，写在 prompt 中。
这个文件依赖哪些对象，写在 prompt 中。
这个文件如何实现，写在 prompt 中。
```

因此，prompt 镜像文件不是辅助材料，而是代码的前置契约。

## 5.3 命名规则

prompt 文件名由真实路径转换而来：

```text
/ 替换为 __
文件名后追加 .prompt.md
```

示例：

| 真实文件                                | Prompt 文件                                                    |
| --------------------------------------- | -------------------------------------------------------------- |
| `src/models/user.py`                  | `prompts/files/src__models__user.prompt.md`                  |
| `src/services/auth_service.py`        | `prompts/files/src__services__auth_service.prompt.md`        |
| `src/controllers/order_controller.py` | `prompts/files/src__controllers__order_controller.prompt.md` |
| `tests/test_auth_service.py`          | `prompts/files/tests__test_auth_service.prompt.md`           |

## 6. 文件级 Prompt 的四个核心部分

每一个文件级 prompt 必须包含四个部分：

```text
输入
输出
设计对象
实现
```

这四个部分是 AI 生成代码前的最低契约。

---

## 7. 第一部分：输入

## 7.1 输入的定义

输入说明当前文件接收什么信息，以及这些信息来自哪里。

输入不是简单列参数，而是要说明：

```text
谁调用当前文件？
调用当前文件时传入什么？
输入对象遵守什么 schema？
输入数据有哪些约束？
输入为空或非法时如何处理？
```

## 7.2 输入模板

```markdown
## 1. 输入

### 1.1 上游调用方

说明谁会调用这个文件中的函数、类或接口。

### 1.2 输入数据

| 名称 | 类型 | 来源 | 是否必填 | 约束 | 说明 |
|---|---|---|---|---|---|

### 1.3 依赖的外部状态

说明是否依赖数据库、缓存、环境变量、配置文件、第三方服务。

### 1.4 非法输入处理

说明输入缺失、格式错误、状态非法时如何处理。
```

---

## 8. 第二部分：输出

## 8.1 输出的定义

输出说明当前文件完成工作后向外部交付什么结果。

输出必须明确：

```text
返回什么对象？
写入什么数据？
调用什么下游模块？
抛出什么错误？
是否改变系统状态？
```

## 8.2 输出模板

```markdown
## 2. 输出

### 2.1 返回结果

| 名称 | 类型 | 接收方 | 说明 |
|---|---|---|---|

### 2.2 状态变化

说明当前文件是否会创建、修改、删除任何数据。

### 2.3 下游调用

说明当前文件会调用哪些模块、服务、接口或工具函数。

### 2.4 错误输出

| 错误码或异常 | 触发条件 | 处理方式 |
|---|---|---|
```

---

## 9. 第三部分：设计对象

## 9.1 设计对象的定义

设计对象说明当前文件围绕哪些对象工作。

对象不是变量名，而是系统中的稳定概念。

例如：

```text
User
Order
Trade
Deployment
Environment
Pipeline
Config
Session
Permission
```

## 9.2 设计对象必须回答

```text
这个对象是什么？
它由谁创建？
它有哪些字段？
它有哪些状态？
它和其他对象是什么关系？
当前文件允许对它做什么？
当前文件不允许对它做什么？
```

## 9.3 设计对象模板

```markdown
## 3. 设计对象

### 3.1 主要对象

| 对象名 | 含义 | 来源 | 当前文件对它的责任 |
|---|---|---|---|

### 3.2 对象字段

| 对象名 | 字段名 | 类型 | 约束 | 说明 |
|---|---|---|---|---|

### 3.3 对象状态

| 对象名 | 状态 | 含义 | 可由当前文件设置 |
|---|---|---|---|

### 3.4 对象关系

说明对象之间的包含、依赖、引用、状态影响关系。

### 3.5 禁止修改的对象内容

说明当前文件不能修改哪些对象、字段或状态。
```

---

## 10. 第四部分：实现

## 10.1 实现的定义

实现说明当前文件内部应该如何完成任务。

实现不是直接贴代码，而是给 AI 的代码生成约束。

它必须说明：

```text
应该包含哪些类和函数。
每个函数的职责是什么。
处理步骤是什么。
异常如何处理。
日志如何记录。
测试如何验证。
禁止做什么。
```

## 10.2 实现模板

```markdown
## 4. 实现

### 4.1 文件职责

一句话说明该文件唯一职责。

### 4.2 不负责的内容

列出该文件禁止实现的内容。

### 4.3 主要类和函数

| 名称 | 类型 | 输入 | 输出 | 职责 |
|---|---|---|---|---|

### 4.4 执行流程

1. 第一步。
2. 第二步。
3. 第三步。

### 4.5 异常处理

说明每类异常如何处理。

### 4.6 日志要求

说明是否需要日志，日志记录什么，不记录什么。

### 4.7 测试要求

说明正常路径、异常路径、边界条件如何测试。

### 4.8 禁止行为

- 不允许修改无关文件。
- 不允许新增未确认对象。
- 不允许新增未确认字段。
- 不允许改变接口格式。
- 不允许实现其他文件职责。
- 不允许绕过错误处理。

### 4.9 验收标准

说明代码完成后如何判断正确。
```

## 12. 全局 Prompt

除了文件级 prompt，每个项目还必须有全局 prompt。

全局 prompt 放在：

```text
prompts/global/
```

## 12.1 AI 宪法 Prompt

文件：

```text
prompts/global/00_ai_constitution.md
```

内容：

```text
你是本项目的 AI 辅助软件工程助手。

你不是自由发挥的开发者，而是受项目文档、文件结构、prompt 镜像和测试标准约束的代码生成工具。

你必须遵守：
1. 没有文件级 prompt，不写代码。
2. 没有输入输出定义，不写代码。
3. 没有设计对象定义，不写代码。
4. 没有实现边界，不写代码。
5. 不新增未确认字段。
6. 不改变已确认接口。
7. 不修改无关文件。
8. 不把其他文件职责写进当前文件。
9. 信息不足时先指出缺失项。
10. 每次输出代码后说明验证方式。
```

## 12.2 项目上下文 Prompt

文件：

```text
prompts/global/01_project_context.md
```

内容应包括：

```text
项目名称。
项目目标。
用户角色。
系统边界。
核心业务流程。
非目标功能。
外部依赖。
交付物。
```

## 12.3 编码规则 Prompt

文件：

```text
prompts/global/02_coding_rules.md
```

内容应包括：

```text

目录规则。
错误处理规则。
日志规则。
测试规则。
依赖管理规则。
```

## 12.4 命名规则 Prompt

文件：

```text
prompts/global/03_naming_rules.md
```

```text
对象命名。

```

## 13. Prompt 先行原则

本宪法规定：

```text
任何代码文件被创建之前，必须先创建对应 prompt 文件。
任何代码文件被修改之前，必须先检查对应 prompt 文件是否需要修改。
如果修改改变了输入、输出、设计对象或实现边界，必须先修改 prompt。
```

开发顺序必须是：

```text
写 docs
↓
设计文件结构
↓
写 global prompts
↓
写 file prompts
↓
让 AI 按 file prompt 写代码
↓
审查 diff
↓
运行测试
↓
提交
```

禁止：

```text
先写代码，再补 prompt。
先让 AI 发挥，再整理结构。
先实现功能，再定义对象。
先改接口，再通知别人。
```

## 14. 人与 AI 的分工

## 14.1 人负责判断

人必须负责：

```text
决定需求是否成立。
决定对象是否合理。
决定文件是否需要存在。
决定接口是否稳定。
决定测试是否通过。
决定代码是否合并。
```

## 14.2 AI 负责执行

AI 可以负责：

```text
根据 prompt 生成代码。
根据 prompt 生成测试。
根据错误日志定位问题。
根据 diff 解释变更影响。
根据 schema 检查接口一致性。
根据文档生成模板化内容。
```

## 14.3 AI 必须被约束

AI 不能：

```text
自己扩展需求。
自己调整架构。
自己发明字段。
自己改变接口。
自己合并模块。
自己重构无关代码。
自己忽略测试。
```

---

## 15. 多人协作规则

多人协作时，prompt 镜像结构比代码本身更重要。

原因是：

```text
代码解决当前实现。
prompt 解决协作共识。
```

每个成员必须只在自己负责的文件和对应 prompt 内工作。

如果需要修改别人负责的文件：

```text
1. 先说明原因。
2. 先修改或提议修改对应 prompt。
3. 让负责人确认。
4. 再修改代码。
5. 补充测试。
```

禁止直接改别人文件的实现细节。

---

## 16. 变更规则

任何变更都要判断它属于哪一层：

```text
需求变更。
对象变更。
schema 变更。
接口变更。
文件职责变更。
实现细节变更。
测试变更。
```

变更影响越靠上，越不能直接改代码。

变更顺序：

```text
需求文档
↓
对象文档
↓
schema 文档
↓
接口文档
↓
文件结构文档
↓
prompt 文件
↓
代码文件
↓
测试文件
```

变更记录模板：

```markdown
## 变更目标

## 当前问题

## 修改内容

## 影响范围

## 涉及文件

## 涉及 prompt

## 测试要求

## 验收标准
```

---

## 17. 审查规则

每次 AI 生成代码后，必须审查：

```text
是否存在对应 prompt。
代码是否符合 prompt 的输入定义。
代码是否符合 prompt 的输出定义。
代码是否只处理 prompt 中声明的设计对象。
代码是否越过实现边界。
代码是否新增未确认字段。
代码是否改变接口。
代码是否修改无关文件。
代码是否有错误处理。
代码是否有测试。
```

审查不是可选项，而是 AI 辅助开发的组成部分。

---

## 18. 测试规则

测试不是证明 AI 很强，而是证明 prompt 约束有效。

每个文件级 prompt 的测试要求，至少覆盖：

```text
正常输入。
非法输入。
边界输入。
状态变化。
错误输出。
下游调用。
禁止行为。
```

如果一个文件没有测试方式，说明这个文件的 prompt 还不够清楚。

---

## 19. 提交规则

每次提交应尽量同时包含：

```text
相关 docs 变更。
相关 prompt 变更。
相关 code 变更。
相关 test 变更。
```

如果只提交 code，不提交 prompt，必须说明原因。

推荐提交粒度：

```text
一个对象。
一个接口。
一个服务文件。
一个测试文件。
一个纵向小流程。
```

不推荐提交粒度：

```text
整个项目。
多个无关模块。
大量格式化变更。
没有 prompt 的代码生成。
```

---

## 20. 常见错误

## 20.1 错误一：直接让 AI 写完整项目

问题：

```text
AI 会自己发明结构、字段、接口和异常处理方式。
```

正确做法：

```text
先写总体文件框架，再逐文件写 prompt，再逐文件生成代码。
```

## 20.2 错误二：只有代码文件，没有 prompt 文件

问题：

```text
代码无法追溯设计意图，后续维护只能猜。
```

正确做法：

```text
每个代码文件必须有镜像 prompt。
```

## 20.3 错误三：prompt 只写“帮我实现”

问题：

```text
AI 不知道输入、输出、对象和边界，会自行补全。
```

正确做法：

```text
prompt 必须包含输入、输出、设计对象、实现四部分。
```

## 20.4 错误四：让 AI 修改无关文件

问题：

```text
局部任务变成全局重构，合并风险极高。
```

正确做法：

```text
每次只允许 AI 修改指定文件。
```

## 20.5 错误五：先代码后文档

问题：

```text
文档会变成装饰，不能约束开发。
```

正确做法：

```text
文档和 prompt 先于代码。
```

---

## 21. AI 宪法的最小执行版本

如果时间很紧，至少执行以下最小版本：

```text
1. 先列出项目文件结构。
2. 每个代码文件创建一个 prompt 镜像文件。
3. 每个 prompt 必须写输入、输出、设计对象、实现。
4. 每次只让 AI 根据一个 prompt 写一个文件。
5. 生成后检查 diff。
6. 运行测试或手动验证。
7. 修改代码前先修改 prompt。
```

只要这七条做到，AI 生成代码就会从“随机补全”变成“受控实现”。

## 22. 最终条款

本宪法的根本精神是：

```text
先有世界观，再有地图。
先有地图，再有房间。
先有房间说明书，再建房间。
先有 prompt，再有 code。
```

对于软件工程来说：

```text
需求是目的。
对象是存在。
结构是秩序。
prompt 是契约。
代码是执行。
测试是证明。
```

任何 AI 辅助开发，只要违背这个顺序，都会从工程活动退化成文本生成。

因此，本宪法的最终原则是：

```text
Prompt First, Code Second.
Structure First, Implementation Second.
Contract First, Generation Second.
```
