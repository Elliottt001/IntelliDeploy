### RT-01：需求纠正没有稳定保住已经补齐的内容

**小白解释：** 让系统补“删除后重启不能复活”，它补好了；下一次补“别人不能修改我的笔记”，又把前面的要求漏掉。

证据：最终 Hybrid 的需求重试中，修正未登录写操作与双向隔离后，后一次审阅又发现删除后的刷新/重启持久性缺失。最终 Baseline 也经历先补持久性、再补跨账号写操作的重试。三轮纠正耗尽后两个任务都失败。

源码：[requirements.py](../../backend/app/agent/requirements.py) 的 `compile_requirement()`。下一轮输入保留用户消息与已冻结的上一版需求，加上最新一次错误文字；没有显式携带本次上一轮草稿和累计未关闭问题。这里的 `previous` 是已冻结需求，不能替代当前整理过程的草稿状态。

修复方向：保留当前草稿、已满足要求和未关闭问题，使纠正能累积推进；明确验收项与原文事实的稳定映射。不能用继续增加重试次数代替保留状态。

关闭条件：包含新增、修改、删除、刷新持久、重启持久、跨账号读写隔离的需求，经过多轮纠正仍保留此前已补齐的每项要求；真实 Baseline/Hybrid 都能冻结完整需求。真正遗漏时仍阻塞。

### RT-02：历史遗漏被误当作当前未解决问题

**小白解释：** 作业已经改对了，纸上却还留着“这题没做”的标签，系统因此不给它过。

证据：最终 Baseline 最后一版已有跨账号写操作隔离，独立审阅返回 `missing=[]`，但草稿仍把历史遗漏复制到 `review_missing`，最终门禁拒绝。Hybrid 也出现“独立审阅无遗漏、草稿仍保留旧遗漏”的冲突。

源码：[requirements.py](../../backend/app/agent/requirements.py) 的 `validate_revision()` 将非空 `draft.review_missing` 判为阻塞；[requirements.md](../../prompts/generation/requirements.md) 没有明确历史反馈与本版仍未解决遗漏的区别。

修复方向：定义遗漏的生命周期，绑定当前草稿与审阅结果；已被当前证据关闭的问题应结束，真实未解决问题继续阻塞。需要明确两份审阅信息冲突时如何核对，不能直接清空全部标记或跳过门禁。

关闭条件：旧遗漏已被当前草稿实际修复时可通过；未修复、原文覆盖不全或只声称修复时仍失败。RT-01、RT-02 应一起处理。

### RT-03：必要追问和合理默认的边界不稳定

**小白解释：** 系统已经有平台登录，却反复问用户“要自己注册还是管理员建账号”；有时还没得到回答，下一版就不再问了。

证据：最终 Baseline 进入 WAITING_USER，收到统一预设回答；Hybrid 的首份草稿也提出账号创建问题，但在需求审阅重试中改掉了问题列表，没有进入 WAITING_USER，也没有收到这条回答。起始一句话相同，实际对话不同。

源码：`compile_requirement()` 先独立审阅，随后才检查 `draft.questions`；同时每次纠正会重新产生问题列表。平台身份适配已有实现，需求提示仍允许账号创建方式随模型自行追问。

修复方向：明确哪些事情按平台默认处理，哪些业务选择必须得到回答；必要问题的提出、回答和关闭要可追踪。模型应能给出有依据的默认判断，不能静默丢弃影响关键业务的待答问题。

关闭条件：合理默认无需反复追问；必要问题一次合并提问，收到回答后准确保留；无回答时不能默默改变已明确的业务要求。性能报告必须保留两条路径的实际追问差异。

### RT-04：调大测试输出上限没有解决产品可靠性

历史证据：试跑出现 `output_tokens=8192`、最终内容为空的模型响应。当前 [config.py](../../backend/app/config.py) 的产品默认输出上限已为 8192、每任务模型调用上限仍为 40；规划调用关闭 thinking，实现工具调用保留 thinking。当前真实失败已不再集中在需求阶段，但生成、修复和后置审查仍竞争同一个 40 次上限。

修复方向：按实际模型协议核对思考 token 与最终输出的预算、截断信号、结构化输出要求及有限纠正策略。输出用量和未知结果要保留。测试覆盖更宽的预算不能证明产品默认配置可用，也不能直接全局放宽费用保护。

关闭条件：在明确记录的产品默认配置下，真实需求整理、路线和实现能获得有效回复；截断、空回复和上游异常有准确分类与有限处理。仍然保留预算和调用上限。

### RT-05：Runner 自身的参数校验仍晚于副作用开始标记

证据：第 5 轮模型将 `npm ci` 的 timeout 写成 300000，Runner 按秒校验，要求 1–600。服务端抛出参数校验错误，Worker 最终只看到“执行节点拒绝操作或尚未就绪”。

当前 [execution.py](../../backend/app/jobs/execution.py) 已在调用 Runner 前校验参数并返回纠正反馈，[loop.py](../../backend/app/agent/loop.py) 已复用秒单位 Schema，挡住默认 Worker 的这条错误路径。但 [runner/service.py](../../backend/app/runner/service.py) 仍先保存 `STARTED`，再验证 `CommandArgs`；直接 RPC 的非法命令仍会在尚未执行时留下开始记录。

修复方向：Runner 的可信边界也应在登记副作用开始前验证请求、检查执行器就绪，返回准确且脱敏的错误。校验失败不等于执行结果未知；真正跨过副作用边界后的未知状态仍须保留。

关闭条件：直接 RPC 的非法 timeout/argv 不执行命令、不留下误导性的 STARTED，并返回可区分的参数错误；真实执行后中断仍能正确恢复或等待核对。

### RT-06：最终错误没有解释最后一次具体失败

证据：最终两任务都只返回 `PIPELINE_FAILED / 模型未能整理完整且可核对的需求`。具体是旧标记未关闭、哪项重新遗漏，只能查逐请求记录才能知道。

源码：`compile_requirement()` 重试耗尽后抛出统一 `RequirementInvalid`，没有把最后一次原因与纠正过程作为结构化诊断带出。此前已修复“把审阅漏项传回模型”的问题，但最终失败对操作者仍过于笼统。

修复方向：保存失败阶段、草稿版本、尝试次数、最后未解决问题和证据引用；对用户给出简明失败原因，受权限保护的诊断提供足够排错信息。

关闭条件：不读取模型完整私有日志，也能从授权诊断知道最后卡点；诊断不泄露密钥或其他用户信息，且不会把尚未执行的业务验收描述为失败的业务检查。

### RT-07：一笔模型费用仍未核对完

证据：第 4 轮取消试跑后，仍有 1 笔未取得完整响应的模型请求。11 个实际提交任务的已知模型费用估算为 ¥2.924164，未知部分未包含在这个数中。最后一对自身没有未知请求。

修复方向：核对供应商记录，确认实际费用及本地记录状态；检查取消、Worker 停止和恢复过程中 REQUESTED/UNKNOWN 的归档与核对规则。

关闭条件：这笔请求有明确核对结果或持续可查询的未知记录；不会被算为免费、被重复请求或重复扣费。当前证据表明“未收敛”，尚不足以认定存在重复扣费或账本损失。

### RT-08：检索和路线输入开销偏重
