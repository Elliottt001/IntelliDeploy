# 平台上线、管理与维护运行指南

更新：2026-11-12。对应第11步08-O1→08-O2；当前代码、本机构建与协议检查已落实，真实服务器/执行节点/域名尚未交接，生产发布与节点演练仍为NOT_RUN。完整一期仍需07-E4和06-F4。以下命令由具有服务器权限的操作者在登记目标执行，示例域名不能当实际环境。

## 1. 先登记环境与运行边界

控制面与执行节点使用不同Linux主机。控制面运行PostgreSQL17、FastAPI、Worker、Next.js和Caddy；执行节点运行可信runner、BuildKit、依赖代理和候选TLS入口。生成代码只进入受限容器，不挂控制面卷、云密钥或Docker socket。平台App部署目标继续使用既有Linux/Sealos适配，不自动采购主机。

| 入口 | 访问范围 | 运行方式 |
| --- | --- | --- |
| 平台Web 443 | 公网平台域名 | Caddy→真实Next.js SSR/BFF |
| 平台API 443 | 公网API域名，业务鉴权 | Caddy→内网9000；文档默认关闭 |
| 控制面PG 5432 | Compose control internal网络 | 不发布宿主端口 |
| runner RPC 9443 | 仅登记控制面来源，mTLS＋服务端token | 专用节点宿主网络 |
| 候选9877 | 节点127.0.0.1 | 独立Caddy以候选通配域名/TLS转发 |
| BuildKit 1234 | 节点127.0.0.1和管理内部网络 | 不发布公网端口 |

先核对CPU/内存/磁盘、Linux挂载权限、端口、registry推拉、DNS/TLS及允许修改的目录。平台Web/API与用户应用域名分开，cookie是平台域名的HttpOnly会话。参考一期外部资源准备清单登记绝对文件路径，不把密钥内容交给模型。

## 2. 私有配置与凭据

从仓库根复制`infra/platform/.env.example`及`runtime.env.example`到仓库外，填写`/etc/intellideploy/platform.compose.env`和`platform.runtime.env`，权限600。Compose文件存域名、镜像和凭据目录引用；runtime文件存后台所需环境变量，API/Worker共用它。生产镜像及基础镜像改为实际核对的OCI digest，保留Git提交与image ID记录，不直接把示例tag用于生产发行。

生产DATABASE_URL形如`postgresql+psycopg://intellideploy:已URL编码的密码@postgres:5432/intellideploy`；数据库名不能是dev/test。SECRET_KEY至少32字符且不能使用默认值。`credentials/postgres.password`保存相同PG密码，`credentials/web-session.secret`保存独立的至少32字符Web会话密钥。已有凭据不能在升级时重新生成，否则账号会话及数据库连接会失效。

API/Worker用户UID10001，凭据目录及其后台文件应可由10001读取，目录700、文件600。Web会话文件直接挂为Docker secret，文件所有者UID1000、权限600；Docker Compose的本地文件secret不会自动修正宿主文件所有权。PostgreSQL镜像入口读取自己的password secret。不要把整个控制面凭据目录挂给生成应用。

`DEPLOYMENT_SECRET_FILES`为引用到只读文件的JSON，如`{"ssh-production":"/run/credentials/app-node.key","kube-production":"/run/credentials/sealos.yaml"}`；`DEPLOYMENT_KNOWN_HOSTS_FILE=/run/credentials/known_hosts`保存经过独立核对的SSH主机公钥。部署器启用BatchMode、IdentitiesOnly及StrictHostKeyChecking，支持登记ssh_port；不自动信任新主机指纹。Kubernetes引用读取登记的kubeconfig文件，旧环境变量映射仅为兼容旧配置保留。

补齐模型、身份、runner客户端证书、目标和价格后才能执行真实生成。实例数据库使用登记的独立数据库服务，或固定digest的INSTANCE_POSTGRES_IMAGE伴生服务；控制面PG内网端口不直接向应用节点开放。支付字段沿用开发运行指南的第10步说明，生产通知必须指向真实API HTTPS入口。

## 3. 构建与首次迁移

所有命令在固定提交的仓库根目录执行。填好的Compose env使用绝对路径；查看真实`compose config`时重定向到权限受限文件，避免把runtime密钥输出到聊天或日志。

```bash
docker compose --env-file /etc/intellideploy/platform.compose.env -p intellideploy-platform -f infra/platform/compose.prod.yml config --quiet
docker compose --env-file /etc/intellideploy/platform.compose.env -p intellideploy-platform -f infra/platform/compose.prod.yml build api web
docker compose --env-file /etc/intellideploy/platform.compose.env -p intellideploy-platform -f infra/platform/compose.prod.yml up -d --wait postgres
docker compose --env-file /etc/intellideploy/platform.compose.env -p intellideploy-platform -f infra/platform/compose.prod.yml run --rm --no-deps api python -m alembic -c /app/backend/alembic.ini upgrade head
docker compose --env-file /etc/intellideploy/platform.compose.env -p intellideploy-platform -f infra/platform/compose.prod.yml up -d
```

API/Worker同一Python镜像，依赖版本固定，内置Playwright及PG17版pg_dump/pg_restore。Web构建共享请求包和Next standalone，运行`node web/server.js`，包含public及.next/static，不使用静态导出。控制面artifacts/logs/PG和Caddy证书目录使用持久卷，应用代码不访问这些卷。

首次启动API会核对唯一Alembic head；不会create_all或修改旧SQLite。health/live表示进程存活；health/ready检查实时迁移和持久目录可写，不依赖模型余额。Worker和执行节点分别用管理status观察，不能仅用API存活代替队列健康。

## 4. 管理命令及目标预检

管理CLI在服务器权限边界运行，没有公开admin API。以下前缀复用同一私有环境：

```bash
docker compose --env-file /etc/intellideploy/platform.compose.env -p intellideploy-platform -f infra/platform/compose.prod.yml exec api python -m app.admin.cli targets list
docker compose --env-file /etc/intellideploy/platform.compose.env -p intellideploy-platform -f infra/platform/compose.prod.yml exec api python -m app.admin.cli maintenance status
```

通过`targets add --id --kind linux|kubernetes --config-file /run/credentials/target.json`登记目标。JSON包含architecture=amd64、domain_suffix、secret_ref及capacity；capacity必须有cpu_millis/memory_mb/storage_mb和固定digest的gateway_image。Linux另有ssh_host/ssh_user/ssh_port/deployment_root及可选Caddy路径；K8s另有namespace/storage_class/ingress_class。只存引用，不接受内联私钥。注册先为UNKNOWN，`targets check --id`复用实际SSH/RBAC/存储/镜像预检后才标HEALTHY，`targets disable --id`阻止新任务选择，保留已有实例。

`prices import --file /run/credentials/prices.json`读取`{"prices":[{"kind":"execution.millis","version":"运营确定的版本","numerator":1,"denominator":1000}],"skus":[]}`格式。这里的比例只是格式示例，真实售价由测试预算/运营政策登记。价格整数比例及币种校验；既有版本不可改价，SKU商业条件变化创建新ID，不能改历史订单。Stripe SKU登记对应price ID。`prices list`只输出商品和价格。

`users developer grant|revoke --user-id ID`复用现有权限字段并保存OS操作者审计，注册不能自升权限。`jobs inspect --id JOB_ID`读取持久阶段、错误代码、资源状态和报告引用，不输出消息正文、密钥或模型思考，不能直接改为SUCCEEDED。`maintenance run-once`调用相同租约维护tick；`maintenance status`查看认领暂停、队列、近期Worker、维护错误及runner预检状态。

## 5. 独立执行节点安装

在登记Linux节点安装Docker并复制同一提交；从`infra/executor/.env.example`和`runtime.env.example`建立仓库外Compose/runtime文件。填实际runner/proxy/BuildKit/crane/Docker CLI固定镜像、registry目录、mTLS和候选通配TLS证书，节点不保存共享模型Key或控制面DB管理凭据。registry/config.json只交给可信runner/构建器，权限600。

runner-credentials包含server.cert.pem/server.key.pem/client-ca.pem，以及`candidate.fullchain.pem/candidate.key`；RPC证书与候选浏览器TLS用途分开。候选TLS证书需覆盖实际通配域名，续期后替换文件并重载candidate-tls。控制面客户端证书/CA需校验真实runner主机名；不关闭证书验证。

运行器在专用节点有Docker及ext4挂载权限，生成命令仍以10001、无capability、只读根、内部网络及资源上限执行。注册的工作区根目录必须在宿主与运行器容器使用相同绝对路径，并具有shared挂载传播；否则Docker宿主看不到容器内的配额挂载。

```bash
sudo mkdir -p /var/lib/intellideploy-runner
sudo mount --bind /var/lib/intellideploy-runner /var/lib/intellideploy-runner
sudo mount --make-rshared /var/lib/intellideploy-runner
docker compose --env-file /etc/intellideploy/executor.compose.env -p intellideploy-executor -f infra/executor/compose.yml config --quiet
docker compose --env-file /etc/intellideploy/executor.compose.env -p intellideploy-executor -f infra/executor/compose.yml build runner
docker compose --env-file /etc/intellideploy/executor.compose.env -p intellideploy-executor -f infra/executor/compose.yml up -d
```

这些挂载只作用于明确登记的专用目录，加入节点启动配置并在重启后用findmnt核对shared传播。runner使用宿主网络访问本机动态容器端口和BuildKit，9877绑定127.0.0.1，9443仅允许控制面来源并要求mTLS/token；只有可信runner挂Docker socket。候选容器不接触该socket、证书或registry凭据。

依赖代理只允许登记域名；每次连接解析DNS并连接已核对的目的IP，拒绝loopback、link-local/metadata、保留地址及未允许私网。候选访问平台能力只使用限定实例/任务凭据；没有允许的网络条件则明确失败。真实节点必须执行磁盘额度、秘密隔离、元数据阻断和登记能力调用演练，镜像构建及本机协议测试不替代这些结果。

## 6. 发布升级、备份与恢复

升级前记录当前提交、全部镜像digest和唯一Alembic head。先`maintenance drain`暂停新生成任务及实例操作认领，等待status中running_jobs/running_operations为0；如果任务无法完成，停止Worker会保留检查点/租约，让恢复流程核对外部动作，不手工改成功状态。等待期间保持API可读。

备份是私有文件，目录700、文件600。数据库使用pg_dump自定义格式；备份artifacts卷、必要文件/配置/恢复材料，并保存校验和。后台实例/计量写入也需在取一致性文件快照前停止。

```bash
docker compose --env-file /etc/intellideploy/platform.compose.env -p intellideploy-platform -f infra/platform/compose.prod.yml exec api python -m app.admin.cli maintenance drain
docker compose --env-file /etc/intellideploy/platform.compose.env -p intellideploy-platform -f infra/platform/compose.prod.yml exec api python -m app.admin.cli maintenance status
# 确认无正在执行的任务/实例操作后停止后台和API写入。
docker compose --env-file /etc/intellideploy/platform.compose.env -p intellideploy-platform -f infra/platform/compose.prod.yml stop worker api
```

用仓库外备份目录保存`exec -T postgres pg_dump -U intellideploy -Fc intellideploy`的标准输出。artifacts卷名称先从Compose配置核对，用只读临时容器将卷打包到同一私有备份目录；记录恢复需要的UID10001及文件权限。不清理备份前的可恢复任务和用户版本。已有数据备份完成且能读取后再build/pull新镜像和执行唯一head迁移，随后up新API/Worker/Web/Caddy。

升级后先检查API/Web及任务、报告、额度，再`maintenance resume`恢复认领。仅在数据库/格式与旧代码兼容时切回旧digest；不兼容迁移要停止写入并在隔离恢复库验证pg_restore及文件快照，再切换恢复环境。不要直接清空现有库、删卷或声称任意Alembic降级都能恢复数据。

## 7. 引用保护、清理与容量

`cleanup plan`只根据ResourceRecord规划，`cleanup run --action-id ID`或不传ID执行已规划动作；`cleanup register --file`仅供管理员核对归属后登记崩溃遗留资源。支持明确登记的WORKSPACE、EVIDENCE、TEMP_ARTIFACT、执行容器、候选运行目录和执行节点CACHE_IMAGE；不遍历宿主目录猜测归属，不启动registry全局GC。DATA/PVC/VOLUME等用户持久类型不进入自动清理。

活跃/等待/额度暂停任务、当前/候选发布、所有可下载版本源码和报告、社区/副本来源、迁移保护及停止实例持久数据继续保留。镜像按digest核对版本引用，别名也不能绕过保护。失败工作区至少7天、未引用证据至少30天、临候选/执行容器至少静置1小时、未引用缓存/临时材料至少7天。保留时间只能调长；重试和暂停没有自动过期删除。

清理先保存DELETING与操作租约，外部动作前再次查引用；节点复核job/instance/operation标签，删除后核对不存在。远端失联或结果不确定记UNKNOWN并保留记录，下一次先观察已完成效果，避免重复副作用。工作区收集后保留节点tombstone，拒绝旧Worker重新创建；单纯TTL到期只关闭候选浏览器访问，不越过控制面的引用检查。候选停止结果未知时保留数据；仅确认候选容器退出后，才回收该候选独立数据空间，绝不回收生产实例。

日常维护共用数据库租约运行资源清理、周期额度和每日索引；REPOSITORY_SEEDS_FILE与GitHub条件未配置时记录INDEX_NOT_CONFIGURED，不伪装刷新成功。存储余量低于WORKSPACE_MIN_FREE_MB拒绝新工作区，已有进度不被抢删。容量不足先停止接新任务、核对保护引用及扩展登记存储，不能强删暂停任务或用户数据腾空间。

## 8. 验收及日志入口

从有权限的测试机运行：

```bash
PYTHONPATH=backend .venv/bin/python scripts/verify_platform_production.py --base-url https://实际平台域名 --api-url https://实际API域名
```

脚本只读检查live/ready、Web HTML及匿名API拒绝，私有报告保存到artifacts/platform-verification；HTTP检查通过的platform_ready不代表生产演练全通过，报告单列重启/队列恢复、数据恢复、节点边界及两云业务检查为待执行。进一步用同一API/Worker的07-E3评测CLI验证实际应用，包含服务器重启后任务/报告/账本恢复、两类目标核心行为及停止后的数据保留；缺资源为NOT_RUN。

API/Worker日志为白名单JSON，仅输出关联ID、阶段/代码/耗时等运维字段，不输出任意消息、参数、Key、cookie或模型思考。`docker compose logs api worker`查看受大小限制的stdout；logs卷内按UTC日轮转保留7份历史文件。`jobs inspect`和maintenance status定位失败。Web/Caddy错误及TLS状态另通过对应服务日志查看，不公开私人证据目录。

真实服务器、节点、域名及旧发布访问演练未执行时，08-O1真实验收Step 4保持未勾选。08-O2本机临时目录/PG/协议检查与真实节点删除演练分开记录，最终一起进入07-E4/06-F4门槛。
