# IntelliDeploy 产品需求草案

日期：2026-11-09

状态：整体设计已确认；2026-11-10 明确一期保留 A/B/C/D 四条路线，GitHub 检索和评分优先，成熟脚手架与固定技术栈仅约束 D。

配套技术方案：[一期技术设计](superpowers/specs/2026-11-09-intellideploy-phase1-design.md)

## 1. 产品目标

用户用自然语言提出软件需求，平台找到并利用现成开源代码，或生成新的代码，最终交付一个真正可以使用的 Web 应用。用户可以继续对话调整应用，也可以把应用发布到社区。

目标用户首先是不懂技术、但有具体需求的人。产品向用户展示需求、结果和费用；仓库检索、选路、代码修改、构建、测试、部署和失败修复在平台内部自动完成。

成功意味着用户的核心操作能完成，所需数据能持久保存，应用有真实可访问的地址。生成文件、构建通过、容器启动分别是过程状态。

## 2. 已确认的范围

| 决策 | 一期范围 |
| --- | --- |

| 交付应用形态 | Web 应用，适配电脑和手机浏览器 |
| 使用场景 | 个人工具及多人应用 |

| 选路与执行 | 系统自动选择并执行；可以少量追问业务问题 |

| 托管 | 平台托管；用户无需准备云资源 |

| 常用能力 | 账号与权限、数据存储、文件存储、AI 调用、联网搜索 |
| 社区 | 应用可选择发布；其他人可以直接使用，也可以创建独立副本 |
| 访问门槛 | 按功能决定；公开体验可以匿名，个人数据或个人额度等操作需要身份 |
| 平台收费 | 免费额度、订阅套餐、按量购买额度 |
| 共享应用费用 | 发布者选择自己承担，或由访问者使用自己的额度 |
| 模型 | 直接使用 DeepSeek 官方 API，平台实现工具执行循环 |
| 速度 | 简单需求尽快交付；复杂需求可后台执行更久 |

二期：创作者变现、额外的运维保障、应用维护、长期服务化的需求修改、为用户生成原生手机 App 和桌面程序。云资源自动购买、开通和释放不属于一期要求。

一期包含用户自行发起的继续对话调整，按平台用量规则计费，不按交付后的时间自动关闭此能力。二期的长期服务在此基础上扩展主动维护、委托式持续开发、服务承诺和独立服务订单。不能因为功能缺失就把首次交付缺陷转成二期付费项目。

## 3. 用户主流程

1. 用户输入想做的应用；未登录可以描述需求或体验公开应用，开始创建、调整或使用个人额度前登录平台。
2. 系统只追问影响核心功能且无法合理推断的业务信息，例如数据是否公开。框架、仓库、数据库和部署方式由系统选择。
3. 系统保存需求和验收清单，自动检索、选路并执行。
4. 用户看到简明状态，例如“正在准备应用”“正在验证功能”；可以关闭页面后回来继续查看。
5. 平台验证应用、部署到真实资源，再验证实际访问。
6. 交付页提供“打开应用”“继续调整”“发布到社区”，并显示简短功能说明和本次用量。
7. 用户提出调整时，系统沿用该应用的需求、源码和数据继续处理。

用户不需要理解 Dockerfile、Kubernetes、模型工具调用或构建日志。执行失败时，用户能看到可理解的原因和下一步；内部诊断材料保留给平台排查。

## 4. A/B/C/D 四条产品路线

| 路径 | 条件 | 行为 |
| --- | --- | --- |
| A：现成应用部署 | 一个仓库已覆盖核心需求 | 准备部署配置和必要的平台接入，验证后部署 |
| B：单仓库改造 | 一个仓库可作为主体，存在可补齐的功能缺口或问题 | 修改、补功能、修复，验证后部署 |
| C：多仓库或组件整合 | 不同项目或组件可提供关键能力，整合具备可行性 | 协调接口、账号、数据、依赖及运行方式，整合成完整应用 |
| D：成熟脚手架生成 | 充分检索和复用评估后没有合理方案，或用户明确要求直接生成 | 使用 Next.js/TypeScript/PostgreSQL/Prisma 成熟脚手架，实现具体业务 |

以上 A/B/C/D 是产品路线。旧代码中 Decision.D 的信息不足/人工处理出口不代表产品 D；澄清、失败和暂停另用任务状态表示。A/B/C 保留实际项目的合理技术栈，D 统一使用成熟脚手架；不会把已有合适项目强制改成 Next.js。

默认先检索和评估 GitHub 上可复用的成果。能满足需求且评分合适时优先 A；存在合理改造空间时评估 B；多个项目或组件能组合时评估 C。只有复用方案不合适或成本不可接受时才用 D，不能因为 D 更容易实现就跳过检索。允许根据真实证据调整路线。

### 检索与评分要求

- 将业务需求转换为原始关键词、英文表达、同义词和应用类别，多路查询；不能只用一句中文或一个过严查询决定结果。
- GitHub 实时检索和已验证项目/README 索引互补。先扩展召回，再阅读候选 README、目录、依赖、运行配置和关键代码。
- 需求匹配、可部署性和工程质量分别评分，保留证据与缺失项。Stars 和更新时间是辅助信号，低星或长期少更新不直接判为垃圾项目。
- 相关框架/库与完整应用分开评估：框架能用于 B/C，但不能因高星冒充符合需求的现成应用。
- 评分表示选择依据，不表示成功概率。核心功能缺失及未知信息必须明确，不能用热度抵消需求不匹配。
- 超时、限流或读取失败不等于没有合适项目，应重试或报告可重试故障，不能直接转 D。
- 进入 D 前保存查询覆盖、候选评估和不采用复用方案的原因。验收包含已知合适项目应被召回、优先复用及避免过早生成的回归案例。

## 5. 交付与继续调整

以下为建议的一期验收规则：

- 每次生成有一份具体的核心功能验收清单，记录输入、操作和预期结果。
- 原始需求中的核心功能必须通过实际验证；界面占位、固定演示数据不能充当已实现功能。
- 应用需要保存的数据，在刷新页面和运行服务重启后仍然存在。
- 多人应用按需求隔离用户数据，公开数据和私有数据有明确权限。
- 依赖 AI、联网搜索或文件上传的功能，至少完成一次真实集成调用验证。
- 平台实际部署、验证访问地址后才能将交付记录标记为成功。
- 调整生成新的候选版本，通过验证后发布；当前可用版本继续提供服务。
- 修改数据结构时保留现有数据，并验证迁移；无法安全迁移的改动不能自动发布。
- 未完成的任务不得用模拟部署、假链接或部分功能替代成功结果。

一期没有给出统一的生成时长承诺，也没有确认 95% 成功率。以实际样本记录耗时、费用和成功率，再决定对外承诺。

## 6. 社区发布和使用

应用默认不公开，创建者可以选择发布。公开页包含应用名称、用途、功能、预览、创建者和使用入口。公开页不暴露源码中的凭据、私有数据和内部执行日志。

“直接使用”进入发布者的同一个实例。应用按业务需要识别不同访问者，不能把多人应用的数据默认混在一起。

“创建我的副本”复用一个验证通过的应用版本，创建独立应用、配置、数据空间和运行实例。默认不复制发布者或其他使用者的数据、账号和密钥。创建副本无需重复从零生成代码，但需要验证新的实例配置及实际部署。

访问规则按功能设置。匿名用户可以打开公开内容或进行发布者允许的有限体验；保存个人记录、访问私有内容、创建副本、消费个人额度等操作需要登录。建议使用统一的平台账号，并将最近使用、收藏、创建的应用保存在“我的应用”中。

发布者可以承担共享应用的调用费用并设置额度限制，也可以要求访问者使用自己的额度。一期的访问者付费是购买平台用量；应用门票、作者定价、分成和提现留到二期。

## 7. 平台能力

| 能力 | 用户侧价值 | 一期要求 |
| --- | --- | --- |
| 身份与权限 | 进入不同应用，保存各自的数据 | 提供统一身份接入方式；已有应用的账号系统需评估实际集成方案 |
| 数据 | 保存记录、历史、配置 | 独立数据空间与持久化；既有仓库所需数据库按应用实际需求部署 |
| 文件 | 图片、附件等上传与读取 | 按应用和权限区分文件；新版本发布不丢失文件 |
| AI | 对话、分析、内容生成 | 平台提供模型能力，按应用、调用者和付费方记录用量 |
| 联网搜索 | 获取实时信息 | 提供搜索和网页内容获取，保存结果来源，并记录实际用量 |

平台默认模型为 DeepSeek。模型或搜索不可用时应报告暂时故障，不能用虚构结果冒充真实调用。

## 8. 额度、订阅与托管费用

免费额度、订阅额度和购买额度统一进入用量账户，套餐及单价可配置。生成、继续调整、创建副本、应用运行中的模型和搜索调用分别记录。

实施计划阶段补充确认：国内和国际收款都支持，渠道包括支付宝、微信支付和 Stripe。先完成额度与套餐管理，再接实际收款；这是一期内的施工顺序，创作者收益和提现仍属于二期。

建议区分以下项目：

- 生成或调整：模型与执行环境用量。
- 部署或创建副本：构建和部署用量。
- 基础托管：运行资源及存储，由实例拥有者承担。
- 应用内能力：由发布者选择发布者或访问者承担。

自动执行不代表无限消费。开始执行前检查并预留额度，运行中执行预算限制；余额不足时保存进度并提示补充额度。充值后由用户发起继续，不能无依据扣费或无限重试。

以下属于本草案的计费建议，需整体评审：额度按实际用量结算，未使用的预留额度释放；系统自身导致的重复执行不重复扣费，平台故障可产生返还记录。失败任务的可计费范围需在启动界面和账单中明确说明。具体售价、套餐额度和免费额度在成本实测后配置。

## 9. 平台托管的一期底座

一期包含让已交付应用正常使用的底座：持久数据、运行进程自动重启、基本实例状态、资源限制、发布验证及手动停止或删除。

二期的额外运维服务包括主动排障、备份恢复服务、扩容服务、应用升级、安全更新和明确的服务承诺。发布时的数据保护和基本运行机制属于一期交付要求。

用户删除应用需要确认，明确同时删除哪些数据；停止应用不删除数据。原云厂商采购流程由平台在系统外完成。

## 10. 验收样本与指标

一期验收必须同时覆盖四条路径，样本包括个人工具、多人应用、AI 和联网搜索，不能只验证模板首页。

| 场景 | 关键验收 |
| --- | --- |
| 现成笔记应用 | 实际运行、保存记录、重启后记录仍在 |
| 给日记应用增加梦境分析 | 新增分析与历史保存，既有记录仍可读取 |
| 整合记录组件和检索组件 | 两部分的业务流程打通，身份和数据一致 |
| 从脚手架生成实时信息工具 | 联网搜索可调用，来源和结果显示正确 |
| 多人使用 | 两个账号的私有记录相互不可见 |
| 继续调整 | 新版本实现要求，旧数据保留，失败版本不替换当前版本 |
| 社区共享与副本 | 同一实例按权限使用；独立副本没有原实例私有数据 |
| 多云部署 | 同类应用能在 Sealos 和普通 Linux 目标上真实使用 |
| 故障与额度 | 执行可恢复，计费无重复，超预算暂停，失败无假成功 |

记录从输入需求到首次可用的耗时、各路径真实交付率、核心功能通过率、调整成功率、实际成本。产品指标包括公开链接体验转化、创建者复访、应用使用者次周回访及独立副本创建率。

## 11. 平台客户端与测试入口

一期保留 `frontend/` 中的 Expo 手机客户端；Next.js 平台 Web 位于 `web/`。两端使用同一个账号、应用、对话、任务、版本、社区和额度后端。在手机发起的任务可以在 Web 查看或继续调整，反之亦然。保留手机平台客户端与生成原生手机应用是两个不同范围。

两端均提供登录、需求对话、任务恢复、交付结果、继续调整、社区共享/副本和额度入口。调用 API 可以独立完成同一生成链路，不需要先打开客户端。提供开发者评测页和命令行真实评测入口，记录每次生成的业务验证证据；普通用户只看业务状态、结果和用量。

[一期交付与测试说明](一期交付与测试说明.md) 定义可见结果、共用 API 协议、启动命令及验收矩阵。文档中的命令和页面是实施目标，当前代码尚未实现这套新流程。

## 13. 一期交付完整性补充（2026-11-10）

六项衔接方案已经形成实施任务：[规划待办](一期规划待办.md)。这表示方案已补齐，代码和真实验收尚未完成。

用户只描述业务，系统将每条需求与核心验收对应；少量追问后自动检索、实现、启动测试、修复和部署。继续调整默认保留已有功能和数据，明确删除/替换才改变对应要求。交付成功必须核心功能及线上实际访问通过，失败不得降低要求。普通用户预算由平台默认政策及账户额度决定，费用/失败用量规则需可理解地展示。

停止或额度不足后可以补额度并恢复同一应用；停止保留数据，恢复不重复生成；后台持续核对状态与用量。免费额度和套餐周期由系统发放，不要求打开页面触发。取消公开阻止新的社区匿名访问；已公开应用成功调整更新公开版本，失败保留旧版，已有独立副本不自动升级。

一期按受支持的Web运行环境自动交付，保留四条路线和优先检索复用；不承诺所有GitHub仓库都能运行。验收至少12个代表性需求并人工检查需求完整/界面可用，两客户端、两类云、三支付都有真实证据。后续宣传耗时/成功率来自样本测量。流程入口与异常处理见[一期产品流程走查](一期产品流程走查.md)。
