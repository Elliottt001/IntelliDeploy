## 本地实现证据

- 质量汇总器会严格校验必需case与review集合，区分automatic、forced、fixture与NOT_RUN，未知费用不填0。
- `release_ready` 同时要求12例质量样本、四条实际路线、人工需求/可用性review及所有发布必需证据PASS。
- 开发者评测页显示单次持久证据状态和未执行原因，不把夹具或未终态任务计为真实交付。
- 实际运行输出目录为 `artifacts/evaluations/<run_id>/`，报告和证据使用限制权限且保留历史失败，不覆盖。
- 06-F4只读审计确认旧库有4个用户，projects/deployments/analyses/github_accounts均为0，仅缺`is_developer`列；没有写旧库或执行持久库迁移。
- 用户迁移测试覆盖一致性快照、幂等导入、身份/哈希冲突整批回滚和旧业务数据阻塞；密码哈希及kubeconfig不进入输出。
- 缺部署目标时API错误码保持`TARGET_UNAVAILABLE`，Web保留草稿且不显示交付链接；case文件不能自报发布检查PASS，runner只按实际结果派生状态。
- 发布硬门槛包含平台备份/迁移/重启/清理；Web可由跨端case证明，iOS/Android仍必须导入独立原生验收证据，Expo浏览器结果不能替代。
- 算法paired汇总器计算Recall@5、路线正确率、首候选成功、构建次数、review precision、重复副作用、选择P50/P95及交付成功率/费用；不配对、fixture、NOT_RUN、未知费用和资源不一致均保持门禁关闭。
- 本地回归为Phase 1后端427 passed / 3 skipped，Task 16专项28 passed；Web E2E 29项。Expo相关页面专项本地通过，但完整浏览器视觉套件存在既有几何基线和缺artifact服务问题；Expo浏览器预览、三平台导出及fixture联调均不计原生设备或真实发布证据。

真实资源到位后按 `smoke -> quality -> flow -> faults` 顺序执行，再由 `scripts/summarize_phase1_evaluations.py` 和 `scripts/run_phase1_acceptance.py --reviews` 生成最终脱敏报告。
