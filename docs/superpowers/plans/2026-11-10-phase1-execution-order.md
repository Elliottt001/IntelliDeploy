# 一期实施文档的完整执行顺序

更新：2026-11-10。本文将[一期总计划](2026-11-09-phase1-00-roadmap.md)和[产品流程走查](../../一期产品流程走查.md)中的依赖整理为可顺序执行的入口，不新增产品范围或开发任务。具体文件、接口、测试和验收仍以对应子计划为准。

用户已指定：直接在 main 开发，由本 agent 顺序执行，不创建工作树、不使用子代理。

## 1. 如何执行这些文档

`00-roadmap` 是整个一期的总入口，执行前先读它及当前 PRD。不能把 01 到 08 按文件编号逐份全部做完：06 的账本和 07 的客户端基础需要提前实施，支付、完整客户端联调及总验收在后面完成。

下面是推荐的完整执行顺序。每一步先读对应子计划，按任务实施并记录证据；“基础联调”只验证当时已经可用的接口，不能提前将整项最终验收勾为完成。

## 3. 子计划内部顺序

| 文档 | 任务顺序 |
| --- | --- |
| 01 | F1 → F2 → F3 |
| 02 | G1 → G2 → G3 → G5 → G6 → G7 → G4 |
| 03 | D1 → D2 → D3 → D4 → D5 → D6 → D7 |
| 04 | C1 → C2 → C3 |
| 05 | W1 提前做基础；W2 → W3 在主链路后做，回补 W1 完整联调 |
| 06 | F1 提前；F2 → F3 在主链路后；F4 最后 |
| 07 | E1/E2 提前做基础；E3 在真实交付后；E4 在支付、生产和完整客户端验收后 |
| 08 | O1 → O2，位于 E3、支付之后，E4/F4 之前 |

这是本 agent 顺序开发采用的一条可行顺序。没有相互依赖的任务可以调整先后，例如 G6 只依赖 01 与 G1，可提前完成；调整时不得跳过必要前置。04 与 03 的独立基础检查也可分别推进，但 D6 的完整集成必须等 04 能力及额度账本具备。

## 5. 贯穿执行的要求

- 每个任务先做失败检查，再实现、验证并单独提交；按实际证据更新对应子计划，不把“文件存在”当任务完成。
- 基础实现、完整联调、真实验收分别记录。客户端可以使用标明 fixture 的数据联调，但它不进入真实交付或成功率统计。
- 每次增加公开接口，同步 07-E1 的共享 Schema/请求包，再让 Web/Expo 消费同一协议。
- Alembic 迁移始终从当前唯一 head 延长，迁移文件编号不决定任务执行顺序，不清空旧 SQLite 数据。
- 外部配置不足时继续推进不依赖它的实现；相关真实检查记录 NOT_RUN，不能用假链接、模拟部署或跳过检查补成 PASS。
- 一期完整完成包括真实生成/四路线、多人权限、持续调整与数据保留、社区/副本、两类云、三支付、两原生客户端、平台运行及质量复核。局部测试、Web build 或 Expo 网页导出通过不能替代这些结果。

外部条件见[资源准备清单](../../一期外部资源准备清单.md)，运行命令见[开发运行指南](../../开发运行指南.md)。
