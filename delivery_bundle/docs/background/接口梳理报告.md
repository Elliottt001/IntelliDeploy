# IntelliDeploy 接口梳理报告

更新时间：2026-05-09

## 1. 目标说明

本报告基于以下内容整理：

- `Corporate.md`
- `background/*.md`
- 主目录多智能体原型代码
- `IntelliDeploy\backend\app`
- `Deploy11\IntelliDeploy\backend\app`
- `Deploy11\IntelliDeploy\src\agents`
- `Deploy11\IntelliDeploy\fallback`

目标是回答四个问题：

1. 我们需要哪些接口
2. 我们已经实现了哪些接口
3. 还缺少哪些接口
4. 哪些接口虽然写了，但名字、职责或逻辑对不上

---

## 2. 按需求应当具备的接口

结合 markdown 需求，系统至少应具备以下接口类别：

### 2.1 用户与基础配置

- `POST /auth/register`
- `POST /auth/login`
- `GET /auth/me`
- `POST /api/user/settings`
- `POST /api/user/github-token`

### 2.2 GitHub 与项目管理

- `GET /api/github/repos`
- `GET /api/projects`
- `POST /api/projects`
- `GET /api/projects/{project_id}`
- `POST /api/projects/{project_id}/analyze`

### 2.3 多智能体主链路

- `POST /api/sessions/start` 或等价接口：启动一次 Builder/Reviewer/Security 流程
- `GET /api/sessions/{session_id}`：查询 `stage`、`iteration_count`、`is_approved`
- `GET /api/sessions/{session_id}/reviews`
- `GET /api/sessions/{session_id}/security-reports`
- `POST /api/sessions/{session_id}/retry`

### 2.4 降级生成 / 异步生成

- `POST /api/generation/start`
- `GET /api/generation/status/{task_id}`
- `GET /api/generation/artifact/{task_id}`
- `POST /api/generation/feedback`
- `GET /api/generation/deployment/{deployment_id}/tasks`
- `GET /api/generation/deployment/{deployment_id}/events`

### 2.5 镜像构建与部署

- `POST /api/images/build`
- `POST /api/images/push`
- `GET /api/images/methods`
- `POST /api/deployments/start`
- `GET /api/deployments/{deployment_id}`
- `GET /api/deployments/{deployment_id}/status`
- `GET /api/deployments/{deployment_id}/logs`
- `POST /api/deployments/{deployment_id}/retry`
- `DELETE /api/deployments/{deployment_id}`
- `GET /api/deployments/project/{project_id}/list`

### 2.6 前端实时联调

- `WS /ws/deployments/{deployment_id}`
- 最好再有 `WS /ws/sessions/{session_id}` 或等价会话流接口

## 4. 已写代码但还没有真正形成对外接口的能力

这些部分有代码，但还没有变成可稳定调用的正式接口能力。

### 4.1 主目录多智能体原型

主目录已经有这些模块：

- `agent_state.py`
- `builder_agent.py`
- `reviewer_agent.py`
- `security_agent.py`
- `router.py`
- `graph.py`
- `runtime.py`
- `validators.py`

说明：

- 这些文件已经构成内部多智能体流程原型
- 但它们没有接到 FastAPI 路由上
- 因此目前不是前后端可联调的正式接口

### 4.2 `Deploy11\src\agents` 多智能体图

这部分已经具备：

- Builder / Reviewer / Security 节点
- 共识节点
- Healing 节点
- 图执行测试

说明：

- 这是较完整的多智能体实现
- 但目前仅在 `tests/integration/test_multi_agent_graph.py` 中直接调用
- 还没有接入 `backend\app` 的请求主链路

## 5. 仍缺少的接口

### 5.1 缺少“主会话型”多智能体接口

按 markdown 目标，当前仍缺：

- `POST /api/sessions/start`
- `GET /api/sessions/{session_id}`
- `GET /api/sessions/{session_id}/reviews`
- `GET /api/sessions/{session_id}/security-reports`
- `POST /api/sessions/{session_id}/retry`

当前系统虽然有：

- 主目录 `graph.py`
- `Deploy11\src\agents\multi_agent_graph.py`

但都没有提供这一层 REST 接口。

### 5.2 缺少“状态机事件流”接口

当前只有：

- `WS /ws/deployments/{deployment_id}`

仍缺：

- `WS /ws/sessions/{session_id}` 或等价接口
- 或 `GET /api/sessions/{session_id}/events`

也就是说，前端还不能订阅 Builder -> Reviewer -> Security -> Healing 这条状态机事件流。

### 5.3 缺少环境变量确认接口

markdown 要求有：

- `env_candidates`
- 前端确认层

当前缺少明确接口，例如：

- `GET /api/projects/{project_id}/env-candidates`
- `POST /api/projects/{project_id}/env-confirmation`

### 5.4 缺少端口确认接口

markdown 要求有：

- `detected_ports`
- 前端确认层

当前缺少明确接口，例如：

- `GET /api/projects/{project_id}/ports`
- `POST /api/projects/{project_id}/ports/confirm`

### 5.5 缺少统一部署 CRUD 入口

旧版部署入口放在：

- `POST /api/projects/{project_id}/deploy`

新版部署入口放在：

- `POST /api/deployments/start`

说明：

- 两套入口并行存在
- 缺少统一的单一部署发起标准

## 6. 名字或逻辑对不上的地方

这一部分是当前最需要收口的。

### 6.1 主目录状态协议 与 `Deploy11/contracts` 不一致

主目录内部状态使用的是：

- `build_result`
- `review_history`
- `security_reports`
- `latest_review_result`
- `latest_security_result`
- `iteration_count`
- `current_dockerfile`
- `current_configs`
- `artifact_version`

而 `Deploy11/contracts/models/agents.py` 使用的是：

- `BuilderOutput`
- `ReviewerOutput`
- `SecurityOutput`
- `ConsensusState`
- `AgentContext`
- `AgentAction`

问题：

- 两边都合理，但不是同一套协议
- 会导致前后端、图编排、日志层、部署层难以共用字段

### 6.2 状态名不一致

主目录 `graph.py` 使用：

- `thinking`
- `building`
- `reviewing`
- `security_checking`
- `rebuilding`
- `approved`
- `failed`

`Deploy11\src\agents` 使用：

- `Thinking`
- `Building`
- `Reviewing`
- `SecurityCheck`
- `Healing`
- `Finalize`

`contracts` 中又使用大写枚举风格：

- `THINKING`
- `BUILDING`
- `REVIEWING`
- `SECURITY_CHECK`
- `FINALIZE`

问题：

- 同一概念出现三套 stage 命名
- 前端展示和后端判断会产生转换成本和歧义

### 6.3 旧版 `projects/deploy` 与新版 `deployments/start` 语义重叠

旧版：

- `POST /api/projects/{project_id}/deploy`
- 直接从 `Analysis` 发起部署

新版：

- `POST /api/deployments/start`
- 从 `generation task artifact` 发起部署

问题：

- 这是两条不同的部署链
- 一条是“分析后直接部署”
- 一条是“生成产物后再部署”
- 目前没有统一主流程

### 6.4 `generation` 实际上是 “fallback generation”

当前新版路由名为：

- `/api/generation/*`

但其内部实现实际是：

- 调用 `FallbackGenerationClient`
- 对接外部 fallback 服务

问题：

- 路由名看起来像“主生成链”
- 实际逻辑是“降级生成链”
- 命名容易误导

建议：

- 若保留当前设计，可改成 `/api/fallback/*`
- 或补上真正主生成链，再让 `/api/generation/*` 成为总入口

### 6.5 WebSocket 存在，但事件广播逻辑未真正接入部署编排

已存在：

- `websocket_manager.py`
- `WS /ws/deployments/{deployment_id}`

问题：

- `broadcast_log`
- `broadcast_event`
- `broadcast_error`

这些方法存在，但没有在 `DeploymentOrchestrator` 中形成稳定调用闭环。

结果：

- WebSocket 通道有了
- 但实时消息流还没有真正“跑起来”

### 6.6 多智能体图存在，但生产链路未接入

已存在：

- `src/agents/graph/*`
- `tests/integration/test_multi_agent_graph.py`

问题：

- 后端 `generation` 服务目前走的是 `fallback_client`
- 不是 `build_multi_agent_graph`

结果：

- 多智能体图是“可测试模块”
- 不是“线上主流程模块”

### 6.7 fallback 客户端与 fallback 服务入口不对齐

后端假设存在外部接口：

- `POST /api/fallback/start`
- `GET /api/fallback/status/{task_id}`
- `GET /api/fallback/artifact/{task_id}`
- `POST /api/fallback/feedback`

但仓库内目前可见的 `fallback/main.py` 是 CLI 入口，不是 FastAPI 服务。

问题：

- 后端已经按“微服务调用”写好
- 但 fallback 服务本身未明确暴露这些 HTTP 接口

这是当前最明显的接入阻塞点之一。

## 7. 当前建议的统一方案

建议最终只保留一条主线：

1. 项目接入：
   - `POST /api/projects`
   - `POST /api/projects/{project_id}/analyze`
2. 生成主链：
   - `POST /api/sessions/start` 或 `POST /api/generation/start`
3. 状态查询：
   - `GET /api/sessions/{session_id}`
   - `GET /api/generation/status/{task_id}`
4. 事件流：
   - `WS /ws/sessions/{session_id}` 或 `WS /ws/deployments/{deployment_id}`
5. 部署：
   - `POST /api/deployments/start`
   - `GET /api/deployments/{deployment_id}/status`
6. 自愈回流：
   - `POST /api/generation/feedback`

同时建议统一以下命名：

- 内部主状态统一用 `snake_case`
- 统一只保留一套 `stage` 枚举
- 统一只保留一套 Builder/Reviewer/Security 输出模型
- 统一只保留一条部署入口

## 8. 结论

### 已经具备的

- 认证接口
- GitHub 与项目接口
- 自动 Docker / YAML 生成接口
- 基础部署接口
- 新版异步生成接口
- 新版部署状态与日志接口
- WebSocket 通道
- 多智能体图测试实现

### 还缺的

- 主会话型多智能体接口
- 会话事件流接口
- 环境变量确认接口
- 端口确认接口
- fallback HTTP 服务正式入口
- 多智能体图接入生产主链

### 最需要优先修正的

- 统一状态协议
- 统一 `stage` 命名
- 统一部署入口
- 明确 `generation` 与 `fallback generation` 的边界
- 把 WebSocket 真实接进编排与部署流程
