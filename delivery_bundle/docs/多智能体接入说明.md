## 1. 目的

本说明只回答一件事：

如果要把主目录中已经写好的这批 Python 文件：

- `agent_state.py`

## 2. 总体判断

不建议把主目录代码直接塞进 `backend/app` 路由层。

更合理的接法是：

- 把主目录这批代码作为“多智能体执行内核”
- 接入 `Deploy11\IntelliDeploy` 的“生成主链”或“会话主链”
- 由 `backend/app` 暴露 REST / WebSocket
- 由 `backend/app/services/*` 调用这套多智能体内核

换句话说：

- 主目录代码负责：Builder / Reviewer / Security / Router / Graph
- `Deploy11\IntelliDeploy\backend\app` 负责：接口、数据库、部署、日志、WebSocket

## 6. 接口名层面的修改建议

这一部分只列“建议改名”。

### 6.1 `generation` 当前名字过于宽泛

当前已有：

- `POST /api/generation/start`

问题：

- 当前实现基本等于“fallback generation”
- 但将来接入主目录 graph 后，这个名字才成立

建议：

- 如果第一步就接入主目录 graph，则这个路由名可以保留
- 如果短期内仍然主要走 fallback，则建议明确分层：
  - `POST /api/generation/start` 作为统一入口
  - `POST /api/fallback/start` 作为降级入口

---

### 6.2 stage 名必须统一

主目录当前使用：

- `thinking`
- `building`
- `reviewing`
- `security_checking`
- `rebuilding`
- `approved`
- `failed`

`Deploy11\src\agents` 当前使用：

- `Thinking`
- `Building`
- `Reviewing`
- `SecurityCheck`
- `Healing`
- `Finalize`

`contracts` 当前偏向：

- `THINKING`
- `BUILDING`
- `REVIEWING`
- `SECURITY_CHECK`
- `FINALIZE`

建议统一为一套，优先建议内部统一为大写枚举：

- `THINKING`
- `BUILDING`
- `REVIEWING`
- `SECURITY_CHECK`
- `HEALING`
- `APPROVED`
- `FAILED`

对应需要修改的地方：

- 主目录 `agent_state.py`
- 主目录 `graph.py`
- 主目录 `router.py`
- `Deploy11\src\agents\graph\*`
- `Deploy11\contracts\models\common.py`

### 6.3 `security_checking` 应统一成 `SECURITY_CHECK`

建议：

  - `security_checking`
  - `SecurityCheck`

统一一个即可。

主目录用：

## 10. 目前多智能体还缺什么

当前已经接入了一部分服务链路，但多智能体这块还没完全闭环，主要还缺下面几类：

### 10.1 数据库层还缺正式字段迁移

虽然 `generation_task_service.py` 已经开始写入：

- `session_id`
- `iteration_count`
- `is_approved`
- `artifact_version`
- `failure_reason`
- `graph_state_snapshot`

但 `generation_tasks` 表结构还没有正式迁移，后续需要补 Alembic / SQL 迁移。

需要修改的文件：

- `Deploy11\IntelliDeploy\backend\app\models\intellideploy\generation_task.py`
- `Deploy11\IntelliDeploy\backend\alembic\versions\*.py` 或当前项目实际迁移目录

建议正式加到 `generation_tasks` 表里的字段：

- `session_id`
  - 类型：`String`
  - 用途：标识一次完整多智能体会话
- `current_stage`
  - 已有字段，继续沿用
  - 用途：记录当前阶段
- `iteration_count`
  - 类型：`Integer`
  - 用途：记录当前是第几轮 Builder/Reviewer/Security 迭代
- `is_approved`
  - 类型：`Boolean`
  - 用途：标识当前构建结果是否通过
- `artifact_version`
  - 类型：`String`
  - 用途：标识本轮产物版本
- `failure_reason`
  - 类型：`Text`
  - 用途：记录最终失败原因
- `graph_state_snapshot`
  - 类型：`JSON`
  - 用途：保存裁剪后的 graph 状态快照

建议补一张新表，而不是把所有事件都塞进 `generation_tasks`：

- `generation_task_agent_events`

建议字段：

- `id`
- `task_id`
- `session_id`
- `iteration_count`
- `agent_name`
  - 可取：`builder` / `reviewer` / `security` / `router` / `graph`
- `stage`
- `event_type`
- `message`
- `payload`
  - JSON
- `created_at`

具体逻辑：

- `generation_tasks` 只保存“当前最终态”和少量摘要字段
- 详细过程保存到 `generation_task_agent_events`
- `runtime_info["_graph"]` 可以继续保留，但只能作为过渡缓存，不应长期替代表结构

建议的数据写入时机：

1. `POST /api/generation/start` 创建任务时，先写入一条 `generation_tasks`
2. `run_graph(state)` 每产生一个事件，就追加一条 `generation_task_agent_events`
3. 每轮 agent 完成时，更新 `generation_tasks.current_stage`
4. graph 完成后，回填：
   - `iteration_count`
   - `is_approved`
   - `artifact_version`
   - `failure_reason`
   - `graph_state_snapshot`

### 10.3 Agent 状态的持久化还不完整

现在主要是把 graph 结果塞进 `runtime_info["_graph"]` 和部分 task 字段里，但还缺：

- 独立的 agent stage 历史表
- 每轮 review / security 的结构化快照
- 每次构建产物版本的完整追踪

需要修改的文件：

- `Deploy11\IntelliDeploy\backend\app\models\intellideploy\generation_task.py`
- 新增 `backend\app\models\intellideploy\generation_task_agent_event.py`
- 如需要，再新增 `generation_task_artifact_version.py`

建议持久化分三层：

第一层：任务当前态

- 表：`generation_tasks`
- 保存：
  - 当前阶段
  - 当前是否通过
  - 当前 dockerfile
  - 当前运行配置摘要

第二层：事件流

- 表：`generation_task_agent_events`
- 保存：
  - 每一步 agent 的执行事件
  - 每轮迭代的失败原因
  - 每次阶段切换

第三层：产物版本

- 表：`generation_task_artifact_versions`
- 保存：
  - `artifact_version`
  - `iteration_count`
  - `dockerfile_content`
  - `current_configs`
  - `review_summary`
  - `security_summary`
  - `created_at`

具体逻辑：

1. Builder 产出新的 `build_result` 时，写一条 artifact version
2. Reviewer 完成时，把 reviewer 摘要写入：
   - agent event
   - artifact version
3. Security 完成时，把 security 摘要写入：
   - agent event
   - artifact version
4. 如果下一轮迭代重新生成，不覆盖旧版本，而是新增一条 artifact version

这样后面才可以追踪：

- 第 1 轮为什么失败
- 第 2 轮修了什么
- 最终上线用的是哪一版 dockerfile / configs

### 10.4 WebSocket 还缺专门的会话级通道

目前还能先复用 deployment 维度广播，但更合理的是补：

- `WS /ws/sessions/{session_id}`

这样 Builder / Reviewer / Security 的状态更新不会和部署状态混在一起。

需要修改的文件：

- `Deploy11\IntelliDeploy\backend\app\routers\websocket.py`
- `Deploy11\IntelliDeploy\backend\app\services\websocket_manager.py`

建议新增的接口：

- `WS /ws/sessions/{session_id}`

建议 `websocket_manager.py` 增加的能力：

- `connect_session(session_id, websocket)`
- `disconnect_session(session_id, websocket)`
- `broadcast_session_event(session_id, payload)`
- `broadcast_agent_state_by_session(session_id, stage, message, data=None)`

建议保留现有：

- `WS /ws/deployments/{deployment_id}`

两条通道的职责分开：

- `deployment_id` 通道
  - 面向部署、健康检查、自愈
- `session_id` 通道
  - 面向 Builder / Reviewer / Security / Graph 的生成过程

具体逻辑：

1. `POST /api/generation/start` 成功后，把 `session_id` 返回给前端
2. 前端先连 `WS /ws/sessions/{session_id}`
3. `run_graph(state)` 过程中，事件优先广播到 session 通道
4. 如果当前任务已经和 deployment 绑定，则同步广播重要摘要到 deployment 通道
5. 部署失败后，自愈事件继续走 deployment 通道，同时新的生成轮次重新开 session 通道

建议 session 通道至少推这些消息：

- `builder started`
- `builder finished`
- `review failed`
- `security failed`
- `iteration incremented`
- `artifact approved`
- `graph failed`

### 10.6 主图和 fallback 的边界还要再收紧

现在是“主图优先，失败回退 fallback”，这个策略是对的，但还要继续明确：

- 哪些场景必须走主图
- 哪些场景允许 fallback
- 哪些失败要直接回灌到 graph 重跑

目前还没做到完全自动判断，仍然需要后续补策略层。

需要修改的文件：

- `Deploy11\IntelliDeploy\backend\app\services\generation_task_service.py`
- `Deploy11\IntelliDeploy\backend\app\routers\intellideploy\generation.py`
- `Deploy11\IntelliDeploy\backend\app\services\healing_engine.py`

建议明确三种策略：

第一类：必须走主图

- 需要 Builder / Reviewer / Security 完整闭环时
- 需要可解释 review/security 历史时
- 需要把部署失败重新回灌到 graph 时

第二类：允许 fallback

- `graph.py` 导入失败
- 主图运行依赖缺失
- 只是做兜底产物生成，不要求多智能体审查过程

第三类：禁止 silent fallback

- graph 已经启动但中途失败
- graph 已经写入 session/task 事件
- 这类情况不能直接悄悄切到 fallback，否则前端和数据库会看到两套不一致状态

建议加一个显式路由字段：

- `execution_engine`
  - 可取：
    - `main_graph`
    - `fallback`

建议保存位置：

- `generation_tasks.execution_engine`
  - 如果暂时不加表字段，至少写入：
    - `repo_profile.integration_source`
    - `constraints.integration_source`

具体逻辑：

1. `start_fallback_task()` 先判断是否满足主图运行条件
2. 满足则创建 `execution_engine=main_graph` 的任务
3. 主图未启动成功时，才允许创建 `execution_engine=fallback` 的任务
4. 如果主图已经启动成功，后续失败应该走：
   - `send_deploy_failure_feedback()`
   - `_rerun_main_graph_task()`
5. 只有主图根本不可用时，才转 fallback
